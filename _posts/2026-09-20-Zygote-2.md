지난 글([zygote-1-post](https://so-sung.github.io/posts/zygote-1-post/))에서는 Zygote가 왜 전역 개입점이 될 수 있는지, 그리고 Magisk/Zygisk가 부트 시점 `LD_PRELOAD` 조작과 ptrace 기반 주입으로 이 지점을 어떻게 활용하는지를 이론적으로 정리했다. 이번 주는 그 이론을 실기기(Android 9)에 직접 적용해보려다가 예상치 못한 벽에 부딪힌 이야기, 그 과정에서 겪은 도구 간 충돌, 그리고 새로 발견한 연구 방향을 정리한다.

## 0. 오늘 하려는 것 — 이번 주에 실제로 막혔던 지점

Android 9 환경에서 루팅을 시도하면서 아래 두가지가 안된다는것을 알았다.

- **KitsuneMagisk가 안 됨**
- **KernelSU도 안 됨**

왜 안될까.. 원인과 버전 차이를 찾아봤다.

## 1. 왜 KernelSU가 Android 9에서 막혔나

찾아보니 KernelSU는 애초에 **커널 버전**을 기준으로 지원 여부를 나눈다. 공식적으로는 GKI 2.0(커널 5.10 이상)을 타깃으로 하는데, 실무적으로는 이게 **기기 출고 시점 기준 Android 12 이상**을 의미한다. 4.14 이상 구버전 커널도 호환은 된다고 명시돼 있지만, 여기엔 중요한 단서가 붙는다 — "직접 커널을 빌드해야 한다"는 것이다.

Android 9의 최소 LTS 커널 요구사항은 4.4.107 / 4.9.84 / 4.14.42 수준이다. 즉 버전 숫자만 보면 KernelSU가 "호환 가능하다"고 말하는 범위 안에 들어가긴 하는데, 이게 "그냥 zip 파일 하나 플래시하면 끝"이 아니라 **그 기기의 정확한 커널 소스를 구해서 KernelSU 드라이버를 직접 빌드해 넣어야 하는** 작업이다. 에뮬레이터나 특정 구형 기기처럼 커널 소스를 구하기 어려운 환경에서는 이 과정 자체가 막히는 게 당연했다.

> 참고: [KernelSU FAQ](https://kernelsu.org/guide/faq.html) · [KernelSU-Next — GitHub](https://github.com/KernelSU-Next/KernelSU-Next) · [Core kernel requirements — Android Open Source Project](https://source.android.com/docs/core/architecture/kernel/core-kernel-reqs)

## 2. 왜 KitsuneMagisk(Zygisk)가 Android 9에서 삐걱댔나

KitsuneMagisk는 Magisk 기반이라 커널 버전 제약은 KernelSU보다 훨씬 느슨하다. 그런데 Zygisk 자체가 Magisk v24부터 들어간 비교적 최근 기능이고, Magisk v26부터는 최소 지원 Android 버전을 6.0으로 올렸다고 공식 릴리즈 노트에 나와 있었다. 숫자만 보면 Android 9는 그 안에 들어가는데, 실제로는 좀 더 복잡한 사정이 있었다.

GitHub 이슈 트래커를 뒤져보니, Android 9 기기 중에서도 특히 **ramdisk가 없는 기기**에서 Zygisk가 아예 동작하지 않는다는 리포트가 있었다. 이런 기기는 일반적인 Magisk 설치 절차(부트 이미지 패치) 대신 리커버리 파티션을 패치하는 별도 방식을 써야 하는데, 이 방식으로 설치하면 "Requires Additional Setup" 팝업 이후 "setup failed"가 뜨면서 루트 권한 자체는 살아있어도 Zygisk만 영구적으로 비활성 상태로 남는 사례가 보고돼 있었다.

> 참고: [Releases: topjohnwu/Magisk — GitHub](https://github.com/topjohnwu/Magisk/releases) · [Requires Additional Setup / Zygisk never works — Magisk Issue #8230](https://github.com/topjohnwu/Magisk/issues/8230)

## 3. 그래서 우회한 방법 — LSPosed + Hide My Applist, 그리고 Frida 변종 모듈

KernelSU와 KitsuneMagisk의 Zygisk 둘 다 정상 동작하지 않는 상황에서 택한 경로는 **LSPosed**였다. LSPosed는 Android 8.1부터 지원한다고 공식적으로 명시돼 있고, 요구사항도 "Magisk 26000 이상 + Zygisk 활성화" 또는 "KernelSU + Zygisk Next/NeoZygisk" 정도로, Zygisk가 어떤 형태로든 살아있기만 하면 된다는 점에서 구버전 환경에 그나마 유연했다.

여기에 **Hide My Applist(HMA)** 모듈을 LSPosed 위에 설치해서 사용했다.

### 3.1 매니저 APK가 자동으로 안 나온 이유

원래는 Zygisk 모듈을 zip으로 설치하면 관리용 매니저 앱(HMA 앱 아이콘)이 자동으로 나와야 한다고 알고 있었는데, 실제로는 아이콘이 뜨지 않았다. 그래서 모듈이 설치된 경로에서 APK 파일을 직접 꺼내 `adb install`로 수동 설치했다.

찾아보니 이게 즉흥적인 임기응변이 아니라, **공식적으로 안내된 대체 방법**이었다. HMA 프로젝트 자체가 "root 권한 획득에 실패하는 경우, apk 안의 설치 파일을 수동으로 추출해서 `Zygisk-HideMyApplist.zip`으로 이름을 바꾼 뒤 `magisk --install-module` 명령으로 직접 설치하라"고 안내하고 있었고, LSPosed 프로젝트 쪽에서도 "root 사용자의 앱 설치를 막는 일부 기기에서는 `/data/adb/lspd/manager.apk` 경로(혹은 zip 안의 manager.apk)에서 매니저를 수동으로 설치하라"는 동일한 패턴의 안내가 있었다.

> 참고: [Hide My Applist — LSPosed 모듈 레포지토리](https://modules.lsposed.org/module/com.tsng.hidemyapplist/) · [Dr-TSNG/Hide-My-Applist — GitHub](https://github.com/Dr-TSNG/Hide-My-Applist) · [LSPosed v1.5.1 릴리즈 노트](https://www.github.com/LSPosed/LSPosed/releases)

### 3.2 KitsuneMagisk가 될 때는 "Florida"로 우회가 됐다

이번 주 테스트에서 또 하나 발견한 게 있다. KitsuneMagisk가 정상 동작하는 기기에서는, 일반 frida-server 대신 **Florida**라는 anti-detection 빌드의 frida-server를 Zygisk 모듈 형태로 받아서 쓰니 우회가 됐다.

찾아보니 Florida는 frida 공식 소스를 그대로 쓰는 게 아니라, 탐지를 피하기 위한 패치를 따로 적용해서 빌드한 frida-server이고, 이걸 Zygisk 모듈로 패키징해서 부팅 시점에 자동으로 백그라운드에서 띄워주는 방식으로 동작했다. `ZygiskFrida`나 `ksu-frida` 같은 비슷한 계열의 프로젝트들도 있는데, 이쪽은 frida-server 프로세스 자체를 띄우는 대신 **frida-gadget을 Zygisk로 대상 프로세스에 직접 주입**하는 방식이라 접근이 조금 다르다. 공통적으로는 "ptrace 기반 attach를 안 쓴다", "바이너리/포트 이름을 바꿔서 시그니처 탐지를 피한다" 같은 회피 기법을 쓰고 있었다.

> 참고: [thelok1s/florida-zygisk — GitHub](https://github.com/thelok1s/florida-zygisk) · [electrondefuser/ksu-frida — GitHub](https://github.com/electrondefuser/ksu-frida) · [fzer0x/ReShift — GitHub](https://github.com/fzer0x/ReShift)

### 3.3 KitsuneMagisk가 없을 때는 왜 Frida가 꺼졌나 — Zygisk 모듈 충돌 가능성

문제는 KitsuneMagisk가 없는 상태에서였다. LSPosed와 Frida 변종(Florida류) 모듈을 **둘 다** 켰더니, 계속 추적해본 결과 Zygisk 모듈을 두 개 동시에 로드하면서 충돌이 나 하나가 꺼지는 것 같았다. 이 추측이 맞는지 실제 사례를 찾아봤는데, 정확히 같은 조합에서 보고된 이슈들이 있었다.

- Zygisk Next(NeoZygisk 계열)를 쓰는 환경에서 "root Frida Server 데몬을 실행한 상태로 특정 앱을 실행하면, Zygisk Next의 프로세스 특수화(specialization) 단계에서 즉시 네이티브 크래시가 난다"는 리포트가 있었다. DenyList에 이미 등록돼 있어도 발생했고, 다른 Zygisk 모듈(magisk-frida, Shamiko, LSPosed 등)이 먼저 로드되면서 배제(exclusion) 처리가 적용되기 전에 영향을 주는 것 아니냐는 논의가 있었다.
- LSPosed의 후속 프로젝트인 Vector 쪽에서는 더 직접적인 사례가 있었다. "LSPosed 모듈이 켜진 상태에서 frida-server를 실행하면 즉시 멈추면서 에러가 나고, 에러 메시지가 SELinux 관련으로 보인다. LSPosed를 끄면 frida-server가 정상 동작한다"는 이슈가 그대로 보고돼 있었다 — 내가 겪은 것과 사실상 같은 증상이다.
- Zygisk 구현체(ReZygisk) 쪽에서는 좀 더 근본적인 메커니즘도 보였다. frida-gadget을 주입하는 모듈을 설치했는데, 상태 파일(state.json)에는 "로드됨"으로 표시되면서도 실제로는 그 모듈의 컴패니언(companion) 라이브러리가 Zygisk 데몬 프로세스에 매핑되지 않아 `postAppSpecialize` 콜백 자체가 호출되지 않는 버그가 보고돼 있었다. 즉 모듈이 "설치는 됐지만 실질적으로는 로드되지 않은" 상태가 되는 것인데, 같은 모듈이 다른 Zygisk 구현체(NeoZygisk)에서는 정상 동작했다고 한다 — Zygisk "구현체"별로 여러 모듈을 동시에 얹는 안정성 자체가 다르다는 뜻이다.

세 사례를 종합하면, 내가 겪은 "LSPosed + Frida 변종 = 하나가 꺼짐" 현상은 특정 기기만의 우연이 아니라, **여러 Zygisk 모듈이 같은 프로세스 특수화 단계에 동시에 개입할 때 흔히 발생하는 알려진 유형의 충돌**일 가능성이 높아 보인다. 다만 정확히 SELinux 컨텍스트 충돌 때문인지, 컴패니언 프로세스 매핑 실패 때문인지, 아니면 둘 다인지는 내 환경에서 직접 재현해서 로그를 봐야 확정할 수 있을 것 같다.

> 참고: [LSPosed/ZygiskNext Issue #1](https://github.com/LSPosed/ZygiskNext/issues/1) · [JingMatrix/Vector Issue #350 — frida-server fails when LSPosed is enabled](https://github.com/JingMatrix/Vector/issues/350) · [PerformanC/ReZygisk Issue #301](https://github.com/PerformanC/ReZygisk/issues/301)

## 4. 이번 경험에서 나온 다음 연구 주제 — SO 파일 무결성

Frida가 막히는 걸 겪고 나니, 자연스럽게 "그럼 보안 솔루션이 SO 파일 쪽을 어떻게 지켜야 하는가"라는 방향으로 생각이 옮겨갔다. 지난 글에서는 방향성만 던져놓고 끝났는데, 이번엔 각 아이디어를 실제로 어떻게 검증할지 좀 더 구체적으로 계획을 세워봤다.

### 4.1 SO 모듈이 계속 떠 있는지 주기적으로 확인

**아이디어**: SO가 로드 안 되면 앱이 실행 안 되니까, 앱이 실행되는 동안 계속 "이 모듈이 여전히 정상적으로 떠 있는가"를 체크하고, 아니면 앱을 종료시켜야 한다.

**기존 구현 현황**: RASP SDK들이 이미 **연속 모니터링(continuous monitoring)** 또는 "민감한 동작 직전 재검증" 패턴으로 구현하고 있었다.

**구체적 검증 계획**:
- `friatest`에 백그라운드 스레드를 하나 추가해서, `Runtime.getRuntime().availableProcessors()` 대신 `System.loadLibrary` 재호출 또는 `/proc/self/maps`에서 자기 so 경로를 주기적으로(예: 2초마다) `grep`하는 방식으로 "모듈이 여전히 매핑돼 있는가"를 체크하는 코드를 넣어본다.
- Frida로 런타임 중 `dlclose()`를 강제 호출하거나, `Interceptor.replace`로 감시 스레드의 체크 함수 자체를 무력화하는 두 가지 공격 시나리오를 각각 테스트한다.
- **예상**: 감시 스레드 자체도 결국 같은 프로세스 메모리 안에 있는 코드이기 때문에, Frida가 감시 함수의 리턴값 자체를 조작하면 이 방어도 뚫릴 수 있다고 본다 — 즉 "감시 로직 하나"로는 안 되고, 감시 스레드 자체를 여러 개 흩어두거나 난독화해야 의미가 있을 거라는 가설을 세워본다.

### 4.2 SO에 실시간으로 코드가 주입되는지 감시

**아이디어**: SO가 캐시/실행 경로에 올라간 뒤에도, 거기에 Frida 같은 게 끼어들면 실시간으로 잡아내서 경고 후 종료해야 한다.

**기존 구현 현황**: `/proc/self/maps` 스캔으로 frida-agent.so/gum-js-loop 같은 문자열을 찾는 방식, 인라인 후킹 탐지, `.text` 세그먼트가 쓰기 가능 상태로 바뀌어 있는지 확인하는 방식이 이미 여러 라이브러리에 구현돼 있었다.

**구체적 검증 계획**:
- `friatest`의 `nativeIsRooted()` 함수 진입부에 `mprotect` 결과나 `/proc/self/maps`에서 해당 함수가 속한 매핑의 권한(`r-xp` 등)을 읽어오는 코드를 추가한다.
- 아무것도 후킹하지 않은 상태 / Frida `Interceptor.attach`로 인라인 후킹을 건 상태, 두 경우의 권한 값을 나란히 비교해서 실제로 차이가 나는지 직접 확인한다.
- 3.3에서 언급한 Florida/ZygiskFrida처럼 ptrace를 안 쓰는 주입 방식도 같은 매핑 권한 변화를 남기는지 별도로 확인해본다 — ptrace 기반이 아니라고 해서 메모리 흔적까지 안 남긴다는 보장은 없다고 보기 때문이다.

### 4.3 SO의 실행 경로·SHA 값을 정확히 알고 있어야 함

**아이디어**: 정확히 어떤 경로에서, 어떤 SHA 값으로 로드돼야 하는지 미리 알고 있지 않으면, 리패키징 없이도 실행 시점에 경로나 값을 가로채서 조작될 가능성이 있다.

**기존 구현 현황**: 서명 인증서의 SHA-256 검증, `.text` 세그먼트 무결성 확인 등은 이미 구현돼 있었다. 다만 "한 번만 검증"과 "계속 검증"은 다른 얘기라는 걸 알게 됐다.

**구체적 검증 계획**:
- `friatest`에 빌드 시점 `libfriatest.so`의 SHA-256을 상수로 박아두고, 런타임에 `/proc/self/maps`에서 실제 로드된 so 파일 경로를 읽어 그 파일을 다시 해시해서 비교하는 로직을 앱 시작 시점에 1회만 넣은 버전(A)과, 5초 간격으로 반복 확인하는 버전(B)을 각각 만든다.
- 두 버전에 대해 "검증 통과 이후 시점에 Frida로 후킹"했을 때 각각 어느 시점까지 탐지가 안 걸리는지 시간을 재서 비교한다.
- **예상**: A는 앱 시작 직후에만 Frida를 붙이지 않으면 이후엔 사실상 무방비일 것이고, B는 최대 5초의 창(window)이 남을 것으로 예상한다 — 이 "창"의 크기를 줄이는 게 결국 4.4의 TOCTOU 문제와 직결된다고 본다.

### 4.4 실행 중에 같은 이름으로 SO를 바꿔치기할 수 있는가 (TOCTOU)

**아이디어**: SO가 실행되는 도중에 프로세스를 잠깐 멈춰놓고, 같은 이름의 SO 파일로 바꿔치기하는 게 가능한가.

**기존 구현 현황**: 공격 쪽에서 정반대 방향 사례를 하나 찾았다. `soSaver` 같은 도구는 `dlopen`/`android_dlopen_ext` 호출을 가로채고 주기적으로 메모리를 스캔해서, 정상적이지 않은 방식으로 로드되는 라이브러리(런타임에만 나타나거나 암호화된 SO)를 프로세스 메모리에서 통째로 덤프해내는 방식으로 동작했다.

**구체적 검증 계획**:
- 먼저 이게 "파일 시스템 레벨"에서 가능한지부터 좁혀본다. `friatest` 실행 중에 별도 셸에서 `libfriatest.so`가 위치한 경로에 같은 이름으로 다른 내용의 so 파일을 덮어쓰기(`cp`) 시도해보고, 이미 메모리에 매핑된 프로세스가 그 변경을 즉시 반영하는지, 아니면 다음 `dlopen` 시점까지는 영향이 없는지 확인한다. (리눅스의 파일 교체와 메모리 매핑의 관계상, 이미 매핑된 페이지는 영향받지 않을 가능성이 높다고 예상하지만 직접 확인이 필요하다.)
- 그다음 "아직 로드되지 않은 시점"을 노리는 시나리오로 좁혀서, `waitForModuleAndHook`처럼 모듈 로드를 기다리는 스크립트의 타이밍(지난 [frida-native-bypass](https://so-sung.github.io/posts/frida-native-bypass/) 글에서 겪었던 폴링 딜레이)을 역이용해, so가 디스크에서 메모리로 올라오는 그 짧은 구간에 파일을 바꿔치기하는 게 이론적으로 가능한지 검토한다.
- **예상**: 안드로이드의 코드 서명·APK 무결성 검증(v2/v3 서명 스킴)이 이 시나리오를 상당 부분 막고 있을 가능성이 높다고 본다 — 그렇다면 "왜 막히는지"를 링커/패키지 매니저 레벨에서 정확히 짚어내는 것 자체가 이번 실험의 결론이 될 수도 있다.

## 5. 마지막 변수 — 커널수를 Android 9에 맞게 직접 빌드해볼 수 있을까

1번에서 짚었듯, KernelSU가 Android 9에서 안 되는 근본 이유는 "공식 지원 범위 밖"이라서다. 그럼 반대로 **내가 이 기기에 맞는 커널을 직접 빌드해서 KernelSU를 심어볼 수 있을까**를 검토해봤다.

찾아본 바로는, KernelSU 진영에서도 구버전 커널에 대한 커스텀 빌드 가이드를 제공하고 있었다(비공식 GKI 통합 가이드). 다만 체크리스트가 꽤 까다로웠다.

- **기기와 정확히 일치하는 커널 소스**가 있어야 한다 (Android/커널 버전, 보안 패치 레벨까지 일치)
- **보안 패치 레벨**이 특히 중요한데, 구형 패치 레벨의 이미지를 플래시하면 anti-rollback 메커니즘에 걸려 벽돌이 될 수 있다는 경고가 명시돼 있었다
- 작업 전 **원본 스톡 boot.img 백업**이 필수 전제 조건으로 강조되고 있었다

벽돌 위험 자체에 대해서는, KernelSU 공식 문서에서 "부트 파티션 플래시로 인한 벽돌"의 원인을 구체적으로 짚고 있었다. 이미지 포맷이 기기와 안 맞는 경우(예: 기기는 `gz` 포맷인데 `lz4` 포맷을 플래시), AVB(Android Verified Boot) 검증을 꺼야 하는데 안 끈 경우 등이 대표적이었다. 다행인 건, **부트로더가 언락된 상태에서 fastboot로 부트 파티션만 건드리는 경우라면, 대부분 스톡 boot.img를 다시 플래시해서 복구가 가능**하다는 점이었다 — 완전한 하드 브릭보다는 "부팅 안 되는 상태(소프트 브릭/부트루프)"에 머무를 가능성이 높다는 뜻이다. KernelSU 자체에도 부트루프 발생 시 Safe Mode로 모든 모듈을 비활성화하고 복구하는 내장 절차가 있다고 한다.

정리하면, 시도 자체가 완전히 무모한 건 아니지만 — (1) 내 기기와 정확히 일치하는 커널 소스 확보, (2) 보안 패치 레벨 정확히 맞추기, (3) 원본 boot.img 백업 — 이 세 가지가 갖춰지지 않은 상태로 진행하면 리스크가 급격히 커진다는 걸 확인했다. 다음 실험 전에 이 세 가지 전제 조건부터 확보하는 게 순서일 것 같다.

> 참고: [Rescue from bootloop — KernelSU](https://kernelsu.org/guide/rescue-from-bootloop.html) · [awesome-kernelsu — Kernel selection checklist](https://github.com/fynks/awesome-kernelsu) · [Android-Kernel-Tutorials — GitHub](https://github.com/ravindu644/Android-Kernel-Tutorials)

## 6. 아직 확실치 않은 부분

- HMA 적용 이후 Frida가 막힌 게 정확히 SELinux 컨텍스트 충돌 때문인지, 컴패니언 프로세스 매핑 실패 때문인지 아직 내 환경에서 직접 재현해 특정하지 못했다.
- 4.4의 "SO 바꿔치기(TOCTOU)"가 안드로이드 환경에서 실제로 실현 가능한 공격인지, 아니면 이미 링커/서명 검증 레벨에서 막혀 있는 것인지 아직 확인하지 못했다.
- 5번의 커스텀 커널 빌드는 아직 실제로 시도해본 게 아니라 사전 조사 단계다. 이 기기의 정확한 커널 소스를 실제로 구할 수 있을지부터가 불확실하다.

## 7. 앞으로 직접 검증해보고 싶은 것들

1. **HMA 설정 하나씩 끄고 Frida 재시도**: HMA의 각 옵션을 개별적으로 껐다 켜면서, 정확히 어떤 설정이 Frida 연결을 막는지 이진 탐색하듯 좁혀보기.
2. **SELinux 로그 직접 확인**: `dmesg`나 `logcat`에서 `avc: denied` 관련 로그를 필터링해서, LSPosed+Frida 변종 동시 실행 시 정말 SELinux 거부가 발생하는지 3.3에서 세운 가설을 직접 검증.
3. **4.1~4.4에서 세운 구체적 실험**: 위 4번 문단에 정리한 계획들을 `friatest`에 순서대로 구현하고 실측.
4. **커널 소스 확보 가능성 조사**: 지금 쓰는 기기의 정확한 모델명·빌드 번호로 제조사/커뮤니티에 커널 소스가 공개돼 있는지부터 확인 — 여기서 막히면 5번 자체가 다음 단계로 못 넘어간다.

## 마무리 — 오늘 정리한 것과 다음 편

- Android 9에서 KernelSU가 막힌 이유는 버전 자체보다는, 구버전 커널 지원이 "직접 커널을 빌드해야 하는" 조건부 지원이었기 때문이다.
- KitsuneMagisk의 Zygisk가 삐걱댄 것도 순수 버전 문제보다는, ramdisk 없는 기기 등 특정 부트 구조와의 조합에서 발생하는 알려진 불안정성에 가까웠다.
- KitsuneMagisk가 될 때는 Florida 같은 anti-detection frida-server 빌드로 우회가 됐지만, 없을 때 LSPosed와 함께 쓰니 충돌이 났다 — 이건 우연이 아니라 여러 Zygisk 모듈이 같은 특수화 단계에 개입할 때 실제로 보고돼 있는 알려진 충돌 유형이었다.
- SO 무결성에 대한 네 가지 아이디어 각각에 구체적인 검증 계획을 세웠고, 특히 4번(TOCTOU)은 안드로이드 서명 검증이 실제로 막고 있을 가능성까지 열어뒀다.
- 커널수를 Android 9에 맞게 직접 빌드하는 건 무모한 시도는 아니지만, 커널 소스 확보·보안 패치 레벨 일치·백업이라는 세 가지 전제 조건이 없으면 리스크가 커진다는 걸 확인했다.

# Zygote 2 - Why KitsuneMagisk and KernelSU Got Blocked on Android 9, and SO Integrity Verification as the Next Problem

In the last post ([zygote-1-post](https://so-sung.github.io/posts/zygote-1-post/)), I laid out why Zygote can act as a global intervention point, and how Magisk/Zygisk exploits it through boot-time `LD_PRELOAD` manipulation and ptrace-based injection. This week, I tried applying that theory to a real device (Android 9), ran into an unexpected wall, hit a conflict between tools along the way, and found a new research direction.

## 0. What I set out to do today — where I actually got stuck this week

Trying to root an Android 9 device, I hit two blockers back to back.

- **KitsuneMagisk didn't work**
- **KernelSU didn't work either**

I dug into why, and into the version differences involved.

## 1. Why KernelSU got blocked on Android 9

It turns out KernelSU draws its support line based on **kernel version** from the start. Officially it targets GKI 2.0 (kernel 5.10+), which in practice means **the device shipped with Android 12 or later**. Older kernels (4.14+) are listed as compatible too, but with an important caveat attached — "you'll need to build the kernel yourself."

Android 9's minimum LTS kernel requirements sit around 4.4.107 / 4.9.84 / 4.14.42. So by version number alone, it technically falls within the range KernelSU calls "compatible" — but that compatibility isn't "just flash a zip and you're done." It means **obtaining that exact device's kernel source and building the KernelSU driver into it yourself.** On something like an emulator or an older device where the kernel source is hard to come by in the first place, this step is naturally where things stall.

> Reference: [KernelSU FAQ](https://kernelsu.org/guide/faq.html) · [KernelSU-Next — GitHub](https://github.com/KernelSU-Next/KernelSU-Next) · [Core kernel requirements — Android Open Source Project](https://source.android.com/docs/core/architecture/kernel/core-kernel-reqs)

## 2. Why KitsuneMagisk (Zygisk) stumbled on Android 9

KitsuneMagisk is Magisk-based, so its kernel-version constraints are far looser than KernelSU's. But Zygisk itself is a relatively recent feature added in Magisk v24, and the official release notes state that Magisk v26 raised the minimum supported Android version to 6.0. By the numbers, Android 9 falls within that range — but the reality turned out more complicated.

Digging through the GitHub issue tracker, I found reports that Zygisk simply doesn't work at all on certain Android 9 devices — specifically ones **without a ramdisk**. Devices like this need a different installation method (patching the recovery partition) instead of the usual Magisk procedure (patching the boot image), and with that method, there are reported cases where, after the "Requires Additional Setup" popup and a subsequent "setup failed" message, root access itself stays alive but Zygisk remains permanently disabled.

> Reference: [Releases: topjohnwu/Magisk — GitHub](https://github.com/topjohnwu/Magisk/releases) · [Requires Additional Setup / Zygisk never works — Magisk Issue #8230](https://github.com/topjohnwu/Magisk/issues/8230)

## 3. How I worked around it — LSPosed + Hide My Applist, plus a Frida variant module

With both KernelSU and KitsuneMagisk's Zygisk failing to work properly, the path I took was **LSPosed**. It's officially documented as supporting Android 8.1 and up, and its requirements — "Magisk 26000+ with Zygisk enabled" or "KernelSU + Zygisk Next/NeoZygisk" — only need Zygisk to be alive in *some* form, which made it relatively more flexible for an older environment.

On top of that, I installed and used the **Hide My Applist (HMA)** module.

### 3.1 Why the manager APK didn't show up automatically

I'd understood that installing a Zygisk module as a zip should automatically produce a manager app icon (HMA's app icon), but in practice, no icon appeared. So I extracted the APK file directly from the module's install path and installed it manually with `adb install`.

Looking into it, this turned out not to be an improvised workaround at all — it's an **officially documented fallback method**. The HMA project itself instructs: "if you fail to obtain root access, manually extract the installer from the apk, rename it to `Zygisk-HideMyApplist.zip`, and install it directly with the `magisk --install-module` command." The LSPosed project has the same pattern of guidance: "on some devices that block app installs from the root user, install the manager manually from `/data/adb/lspd/manager.apk` (or the manager.apk inside the zip)."

> Reference: [Hide My Applist — LSPosed Module Repository](https://modules.lsposed.org/module/com.tsng.hidemyapplist/) · [Dr-TSNG/Hide-My-Applist — GitHub](https://github.com/Dr-TSNG/Hide-My-Applist) · [LSPosed v1.5.1 release notes](https://www.github.com/LSPosed/LSPosed/releases)

### 3.2 When KitsuneMagisk worked, "Florida" got me past the bypass

One more thing came up this week. On a device where KitsuneMagisk was working properly, instead of a plain frida-server, grabbing an anti-detection build called **Florida**, packaged as a Zygisk module, got the bypass working.

Digging into it, Florida turned out to be a frida-server built from the official Frida source with separate detection-evasion patches applied on top, packaged as a Zygisk module that automatically starts it in the background at boot. There are similar projects in the same family — `ZygiskFrida`, `ksu-frida` — which take a slightly different approach: instead of running the frida-server process itself, they inject **frida-gadget directly into the target process via Zygisk**. What they share in common are evasion techniques like "doesn't use ptrace-based attach" and "renames binaries/ports to dodge signature-based detection."

> Reference: [thelok1s/florida-zygisk — GitHub](https://github.com/thelok1s/florida-zygisk) · [electrondefuser/ksu-frida — GitHub](https://github.com/electrondefuser/ksu-frida) · [fzer0x/ReShift — GitHub](https://github.com/fzer0x/ReShift)

### 3.3 Why Frida got turned off when KitsuneMagisk wasn't there — a likely Zygisk module conflict

The problem showed up specifically without KitsuneMagisk. With LSPosed and a Frida-variant module (Florida and the like) **both** turned on, tracking it further, it looked like loading two Zygisk modules at once was causing a conflict, with one of them getting disabled. To check whether that guess held up, I looked for real-world cases — and found issues reported in exactly this combination.

- In an environment using Zygisk Next (the NeoZygisk family), there was a report that "running a target app while a root Frida Server daemon is active causes an immediate native crash during Zygisk Next's process specialization stage." This happened even with the app already on the DenyList, with discussion around whether another Zygisk module (magisk-frida, Shamiko, LSPosed, etc.) loading first was interfering before the exclusion took effect.
- Vector, LSPosed's successor project, had an even more direct case. An issue reported exactly this: "running frida-server while the LSPosed module is enabled causes it to freeze immediately with an error, and the error appears to be SELinux-related. Disabling LSPosed makes frida-server work normally" — effectively the same symptom I ran into.
- On the Zygisk implementation side (ReZygisk), there was an even more fundamental mechanism at play. A module injecting frida-gadget was installed, and while the state file (state.json) listed it as "loaded," its companion library was never actually mapped into the Zygisk daemon process, so the `postAppSpecialize` callback itself never fired. In other words, the module ends up "installed but not effectively loaded" — and reportedly, the identical module worked fine on a different Zygisk implementation (NeoZygisk). Meaning stability when stacking multiple modules can differ by which Zygisk "implementation" you're actually running.

Putting the three together, what I ran into — "LSPosed + a Frida variant = one of them turns off" — looks less like a coincidence specific to my device, and more like **a commonly reported category of conflict that happens when multiple Zygisk modules intervene at the same process-specialization stage.** Whether it's specifically an SELinux context conflict, a companion-process mapping failure, or both, is something I'll need to reproduce and check the logs on my own setup to pin down for certain.

> Reference: [LSPosed/ZygiskNext Issue #1](https://github.com/LSPosed/ZygiskNext/issues/1) · [JingMatrix/Vector Issue #350 — frida-server fails when LSPosed is enabled](https://github.com/JingMatrix/Vector/issues/350) · [PerformanC/ReZygisk Issue #301](https://github.com/PerformanC/ReZygisk/issues/301)

## 4. The next research topic that came out of this experience — SO file integrity

After running into Frida getting blocked, my thinking naturally shifted toward "so how should a security solution actually protect the SO file side of things?" Last time I just threw out the general direction; this time I worked out a more concrete plan for how to actually test each idea.

### 4.1 Periodically checking whether the SO module is still loaded

**The idea**: if the app doesn't run without the SO loaded, then while the app is running, it should keep checking "is this module still properly loaded," and terminate itself if not.

**What's already out there**: RASP SDKs already implement this as either **continuous monitoring** or a "verify right before a sensitive operation" pattern.

**A concrete test plan**:
- Add a background thread to `friatest` that periodically (say, every 2 seconds) checks whether the module is still mapped — either by re-calling `System.loadLibrary` or by `grep`-ing its own `.so` path out of `/proc/self/maps`.
- Test two separate attack scenarios: forcing a `dlclose()` call at runtime via Frida, and using `Interceptor.replace` to neutralize the watchdog thread's own check function.
- **Prediction**: since the watchdog thread is itself just code sitting in the same process memory, I'd expect Frida to be able to defeat this defense simply by tampering with the watchdog function's return value — meaning a single watchdog isn't enough; scattering multiple watchdog threads and obfuscating them is probably what actually matters, as a hypothesis to test.

### 4.2 Watching in real time for code being injected into the SO

**The idea**: even after the SO has loaded into the cache/exec path, if something like Frida injects into it, that needs to be caught in real time, with a warning and shutdown.

**What's already out there**: scanning `/proc/self/maps` for strings like frida-agent.so/gum-js-loop, detecting inline hooking, and checking whether the `.text` segment has become writable are all already implemented across several libraries.

**A concrete test plan**:
- Add code at the entry of `friatest`'s `nativeIsRooted()` that reads the `mprotect` result or the permission bits (e.g. `r-xp`) of the mapping that function belongs to, from `/proc/self/maps`.
- Compare that value directly between an unhooked state and a state with an inline hook attached via Frida's `Interceptor.attach`, to confirm whether it actually differs.
- Separately check whether a non-ptrace injection method like Florida/ZygiskFrida from 3.3 leaves the same kind of mapping-permission change — since not using ptrace doesn't necessarily mean it leaves no memory trace at all.

### 4.3 Knowing exactly which path and SHA value the SO should load with

**The idea**: without knowing in advance exactly which path and SHA value the SO should load with, there's a possibility of intercepting and tampering with the path or value at runtime, even without repackaging.

**What's already out there**: verifying the SHA-256 of the signing certificate and checking `.text` segment integrity are already implemented. But I learned that "verify once" and "verify continuously" are different claims entirely.

**A concrete test plan**:
- Hardcode the build-time SHA-256 of `libfriatest.so` as a constant in `friatest`, then build two versions: one (A) that reads the actually-loaded `.so` path from `/proc/self/maps` and re-hashes it exactly once at app startup, and another (B) that repeats the check every 5 seconds.
- For both versions, time how long detection can be avoided after attaching a Frida hook post-verification, and compare.
- **Prediction**: I'd expect version A to be essentially defenseless as long as Frida isn't attached at the exact moment of startup, while version B should leave a window of up to 5 seconds — and shrinking that window is, I think, directly tied to the TOCTOU problem in 4.4.

### 4.4 Can the SO be swapped out under the same name mid-execution (TOCTOU)

**The idea**: can the process be briefly paused while the SO is running, and the SO file swapped out for one with the same name?

**What's already out there**: I found a case from the opposite direction, on the attack side. Tools like `soSaver` intercept `dlopen`/`android_dlopen_ext` calls and periodically scan memory to catch libraries loaded through non-standard means (ones that only appear at runtime, or are encrypted), dumping them straight out of process memory.

**A concrete test plan**:
- First narrow down whether this is even possible at the **file-system level**. While `friatest` is running, from a separate shell, try overwriting (`cp`) the file at `libfriatest.so`'s path with a different `.so` under the same name, and check whether the already-running process (already mapped into memory) picks up the change immediately, or whether it only affects the next `dlopen` call. (Given how file replacement and memory mapping interact on Linux, I'd expect already-mapped pages to be unaffected, but this needs direct confirmation.)
- Then narrow toward the scenario of targeting the moment **before** the library has loaded — flipping around the module-load-polling timing I ran into with `waitForModuleAndHook` (from the earlier [frida-native-bypass](https://so-sung.github.io/posts/frida-native-bypass/) post) to examine whether swapping the file during that brief window, as it's being read from disk into memory, is theoretically possible.

## 5. One last variable — could I build a custom kernel matching Android 9 for KernelSU myself

As noted in section 1, the fundamental reason KernelSU doesn't work on Android 9 is being "outside official support." So, the flip side — I looked into whether **I could build a kernel matching this specific device myself and get KernelSU running on it.**

From what I found, the KernelSU community does provide custom-build guides for older kernels (unofficial GKI-integration guides). But the checklist turned out to be fairly demanding.

- You need **kernel source that exactly matches the device** — Android/kernel version, down to the security patch level
- The **security patch level** matters in particular — flashing an image with an older patch level can trip the anti-rollback mechanism and brick the device, according to an explicit warning
- A **backup of the original stock boot.img** before starting is emphasized as a mandatory prerequisite

On the bricking risk itself, KernelSU's own documentation spells out specific causes of "bricking from a boot-partition flash": flashing an image format that doesn't match the device (e.g., the device expects `gz` format but an `lz4` image gets flashed), or failing to disable AVB (Android Verified Boot) verification when it needed to be disabled, among others. The reassuring part: **as long as the bootloader is unlocked and only the boot partition is being touched via fastboot, recovery by re-flashing the stock boot.img is usually possible** — meaning it's more likely to land in a "won't boot" state (soft brick/bootloop) than a true hard brick. KernelSU itself also reportedly has a built-in Safe Mode procedure that disables all modules for recovery if a bootloop occurs.

Bottom line: the attempt itself isn't recklessly unreasonable, but I confirmed that without (1) kernel source that exactly matches my device, (2) matching the security patch level precisely, and (3) a backup of the original boot.img, the risk climbs sharply. Securing these three prerequisites seems like the right order of operations before the next experiment.
